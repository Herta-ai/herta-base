# ADR-003: 采用 Salvo 作为 Web 框架

## 状态

已接受 (Accepted)

## 上下文

HertaBase 旨在提供自动化 OpenAPI 文档和动态 API 路由管理。核心团队在 Rust Web 框架的选型上面临几个关键需求：

1. **原生 OpenAPI 支持**：BaaS 系统的大量动态接口需要能被自动捕获和生成标准文档。
2. **卓越的开发者体验（DX）**：路由配置需要具备极高的灵活性，便于进行动态绑定。
3. **强大的异步与中间件能力**：鉴权、JWT 签发及 API Rules 规则引擎对请求生命周期的拦截有高要求。

## 考虑的替代方案

- **Axum**：Rust 生态中目前最主流、表现最出色的 Web 框架之一。由于背靠 Tokio 团队，质量极高。然而 Axum 自身并没有原生集成 OpenAPI 的能力，需要依赖 `utoipa` 这样的外部宏库，在应对动态 Collection 接口自动推导时往往显得力不从心。
- **Actix-web**：非常成熟且高性能的框架，但大量依赖宏来进行路由和请求上下文管理。且同 Axum 一样，原生的 OpenAPI 支持欠缺。
- **Rocket**：易用性极好，但在最初设计时偏向同步模型，历史包袱较重，面对实时订阅（SSE）和高度异步的并发场景时不具备显著优势。

## 决策

HertaBase 决定采用 **Salvo** 作为其核心 Web 框架，并启用 `oapi` 特性。

## 后果 (Consequences)

### 优势 (Pros)

- **原生集成 OpenAPI**：凭借内置的 OAPI 功能，框架可在定义路由的同时极其方便地生成标准文档，这与 Phase 1 中“OpenAPI 自动生成”的目标完全契合。
- **灵活的 Handler 抽取**：基于宏的强大数据抽取能力让控制器层的逻辑极为干净整洁。
- **人体工学优秀**：优秀的开发者体验使得中间件和动态路由的实现更加直接与高效。

### 劣势 (Cons)

- **社区规模较小**：与 Axum 或 Actix-web 相比，Salvo 的用户基数较小。遇到极端边缘情况或复杂集成时，可供参考的社区文档与开源实践相对匮乏。
