# ADR-001: 采用 SurrealDB 作为核心数据库

## 状态

已接受 (Accepted)

## 上下文

HertaBase 是一个 Backend-as-a-Service (BaaS) 平台。作为 BaaS 系统的核心存储引擎，我们需要一个具备以下特性的数据库：

1. **多模型支持**：需要原生支持文档存储和图关系映射。
2. **实时查询能力**：能够通过监听数据表变更来推送实时事件。
3. **高扩展性**：支持从嵌入式单文件运行平滑过渡到分布式集群部署，适应从小规模应用到大规模生产的需求。

## 考虑的替代方案

- **SQLite**：被同类产品（如 PocketBase）广泛使用。它的优势是单体嵌入非常轻量且易于部署。然而，SQLite 不具备原生的图查询能力，也缺乏内置的实时订阅（Realtime）机制。此外，向分布式架构迁移的成本极高。
- **PostgreSQL**：功能极为强大且成熟，支持丰富的查询和关系模型。但它作为一个重量级的独立数据库服务，无法作为内嵌模式集成在单个二进制文件中执行，与 HertaBase 期望的开箱即用体验相冲突。
- **MongoDB**：支持优秀的文档存储模型，但同样无法实现轻量化内嵌，并且不具备原生图数据库的能力。

## 决策

HertaBase 决定采用 **SurrealDB** 作为系统的底层数据库。
系统在 Phase 1 采用纯 Rust 的 `SurrealKV` 作为嵌入式持久化引擎，并使用内存引擎运行测试；在未来需要大规模分布式部署时，将通过适配 `TiKV` 支持集群模式。

## 后果 (Consequences)

### 优势 (Pros)

- **多模型聚合**：原生支持图模型与文档模型，极其适合构建动态 Collection 与复杂数据关联。
- **实时事件订阅**：具备内置的 `LIVE SELECT` 功能，极大地简化了 HertaBase 实时推送引擎的架构。
- **灵活的部署形态**：兼具嵌入式（SurrealKV）和未来分布式（TiKV）形态，契合项目从开发期到生产期的演进路径。

### 劣势 (Cons)

- **生态系统较新**：作为一个相对年轻的数据库，社区沉淀和可参考的大规模生产案例不及传统数据库。
- **潜在的稳定性风险**：由于处于快速迭代期，某些边缘特性可能会引发不确定性的问题，需要团队花费精力去追踪和解决。
