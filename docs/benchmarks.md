# 基准测试与性能目标

本文档阐述 HertaBase 的架构性能预期、理论优势以及未来的基准测试方法学。

## 1. 声明

> **注意**: 具体的基准测试数据计划在 HertaBase 达到 MVP（最小可行性产品）阶段后公布。本文档目前侧重于说明性能目标与测试方法。

## 2. 性能设计目标

HertaBase 以 Rust 构建微内核，系统设定了极具竞争力的性能目标：

- **吞吐量**：在标准消费级硬件上，针对简单的 CRUD 接口操作吞吐量目标达到 >10,000 requests/sec。
- **延迟指标**：针对单记录操作，p99 延迟目标控制在 <5ms 以内。
- **资源占用**：系统闲置时内存开销 <50MB。
- **分发体积**：可执行文件剔除调试符号并压缩后体积 <30MB。

## 3. 计划中的基准测试方法学

- **测试工具**：将采用 `wrk2` 或 `k6`。
- **覆盖场景**：基本 CRUD 操作、用户认证全流程、大规模 SSE 并发长连接以及 JS Hook 高频触发等场景。
- **测试环境**：运行在标准化虚拟机（如 AWS EC2 基础实例）环境内以确保数据可复现。
- **横向对比**：将与市面上的同类方案（如 PocketBase、Supabase Self-hosted、Directus）进行对照测试。

## 4. 理论性能优势

HertaBase 设计之初即拥有较多性能层面的架构优势：

- **相较于 Go (如 PocketBase)**：Rust 提供了零成本抽象与无 GC (Garbage Collection) 停顿的极度稳定时延特性。
- **嵌入式数据库特性**：SurrealDB 的嵌入式模式在处理本地查询时消除了传统 C/S 数据库中不可避免的网络 I/O 及协议序列化开销。
- **JS 引擎对比**：使用 `rquickjs` 引擎提供了微秒级的冷启动速度，远超 V8 引擎毫秒级的启动开销。
- **单体极简部署**：单一的二进制程序，无冗杂的中间件堆栈依赖。

## 5. 已知的性能考量点

- **跨语言序列化开销**：在 Rust 核心与 JS 运行时之间进行数据交换，JSON 序列化可能会成为瓶颈。
- **缓解策略**：系统在设计中引入零拷贝内存机制，并鼓励开发者进行选择性 Hook 挂载（仅在需要时触发 JS 引擎）。

## 7. 性能调优指南

在生产环境中，系统管理员可以通过修改启动配置来调优以适应特定负载：

- 调整底层 RocksDB 的缓存与刷盘策略。
- 自定义 rquickjs 的运行实例池大小与并行处理容量。
- 配置最大 TCP 连接限额及 Salvo Web 框架的并发数设定。
